## 3. New code — audit by file

### 3.1 `cloud/db/src/derive-v3.ts` (188 lines) — ORPHANED PIPELINE FIX ✅

This is the answer to the biggest finding from V3_AUDIT.md. `repository-v3.ts`'s write functions
had zero non-test callers. `deriveV3FromDigest` is the missing producer.

**What it does**: For every non-group relationship in a digest, derives a `persons` row (contact_id
→ person_id via deterministic hash), an `identities` row (source=imessage, confidence=exact), an
`interactions` row (direction from sent/received counts, meta carries relationship_kind in jsonb
because no v3 column exists yet), and a `relationship_metrics_daily` row.

**Design decisions that are correct**:
- `person_id` reuses the already-salted `contact_id` hash under a `p_` prefix. Deterministic and
  idempotent — the same contact always maps to the same person across every digest.
- Group threads (`is_group: true`) are skipped. Correct: you cannot interview a group chat about a
  single human's relationship.
- Own transaction, swallowed on failure. The digest itself must never be lost to a bug in this
  newer code. A stale v3 cache is a strictly better failure mode than a rolled-back digest ingest.
- `relationship_kind` carried in `interactions.meta` (jsonb) because no v3 column exists. Documented
  in INTERFACES.md. Whoever adds the real column can backfill from there.
- `median_gap_days` set to null because no cadence-gap field exists in the digest. Does not invent
  a value — this is the right null discipline.
- Content ref is null. Never reads or logs real message content. Correct.

**What could go wrong**:
- `deterministicInteractionId` uses `digest_id + person_id` hash. If the Mac uploads the same digest
  twice with different digest_ids (the production duplicate path), each digest produces a different
  interaction_id, so `on conflict ... do nothing` won't deduplicate. This is actually correct —
  each digest IS a distinct ingestion event — but it means interactions accumulate per-digest rather
  than per-relationship. The idempotency test (`second.interactions === 0`) only holds for re-runs
  with the same digest_id.
- `median_reply_latency_s` fields are typed as optional in the digest. The null-coalescing is
  correct but the `!` assertion on `maya.median_reply_latency_s!.user!` in the test assumes the
  fixture always has these fields. Not a code bug, but a test fragility to flag.

### 3.2 `cloud/agent/src/verifier.ts` — general-tool defense ✅

Two changes:
1. **Pure general-knowledge turns must not read as malfunctions** (commit `9e79f6c`). If every tool
   call is "general", the verifier now recognizes this and doesn't flag the absence of person-bearing
   evidence as a defect.

2. **The `general` tool's output is excluded from name and handle verification** (commit `a232a89`).
   Free-text model output via `general` can contain any string, including a person's name. If that
   string were allowed to verify claims, the model could fabricate a person, cite `general`, and pass
   I2. The fix: `general`-sourced leaves populate `words`/`numbers`/`rawStrings` but NEVER `names`
   and NEVER `handleRawStrings`. Belt (output shape has no `display` field) and suspenders
   (buildEvidencePool excludes it from the verification pool).

**Residual risk, disclosed rather than hidden**: The PROPER_NOUN_RE regex cannot distinguish
"Maya" (a person) from "Paris" (a city). Every `general` answer mentioning a capitalized proper
noun will routinely fail first-pass and escalated verification and degrade — costing an extra
round-trip and showing as `degraded` in telemetry. The user still gets the correct answer (via
`renderGroundedSummary`'s `general` case which restates verbatim), but precision is traded for
safety. This is the correct tradeoff.

### 3.3 `cloud/agent/src/agent-loop.ts` — refusals offer alternatives ✅

The refusal text now lists real capabilities instead of dead-ending: "I can look up someone's
relationship status, search your messages, check open loops, see who's overdue, or answer a
general-knowledge question — want to try one of those instead?" When tool calls were made but
exhausted, it uses `defaultDegrade(calls)` to restate what the tools actually returned rather than
the bare refusal string.

The system prompt now explicitly instructs the model to never use `general` for person-specific
questions and to disclose when it's giving stale model knowledge.

### 3.4 `cloud/api/src/messages-access-alert.ts` (74 lines) — fleet-wide alarm ✅

The heartbeat now sends a text when `messages_access_state: "lost"` arrives. Gated to fire once
per loss EPISODE (`LossEpisodeGate`), not once per heartbeat. Never allowed to fail the heartbeat
(a Mac struggling to report `lost` must not also get 400s).

**Design**: `idempotency_key` scoped to `userId + deviceId + episodeKey`. Contrast with
`firstSyncOffer`'s `firstsync-${userId}` (one-per-account-ever). Correct — a user can lose and
regain access multiple times.

### 3.5 `mac/Sources/BoiApp/BoiApp.swift` + setup screen — Contacts fix ✅

Three problems fixed, one commit:
1. Setup screen was unreachable (FDA check bypassed it unconditionally). Now keys on whether

2. Contacts step couldn't grant anything. AddressBook SQLite reads fail even with FDA — Contacts

### 3.6 Schema test additions (234 lines)

New `v3 derivation` describe block with 5 tests:

## 8. Items missed or needing flagging (new from this audit)

### ⚠️ 1. `deriveV3FromDigest` runs once per ingest — closed-loop only

Derivation runs when a new digest arrives (ingest-worker.ts). This is correct for incremental sync.
But there is no backfill path — if the Mac has 6 months of history, only future digests populate
the v3 tables. The initial sync populates `digests` and `relationships` (via insertDigest) but
`persons`/`identities`/`interactions`/`relationship_metrics_daily` only fill from that point forward.

**Severity**: Medium. The agent will work correctly for new relationships and progressively fill
for existing ones as digests arrive. But it won't have full history on first launch. Either
acceptable (startup cold-start) or needs a one-time backfill job. Document the expectation.

### ⚠️ 2. `deterministicInteractionId` across digest re-uploads

As noted in §3.1, if the Mac re-uploads the same digest with a different `digest_id` (the production
duplicate path), the interaction gets a different `interaction_id` and inserts a new row. `on
conflict ... do nothing` won't deduplicate. The idempotency test passes only for re-runs with the
same `digest_id`, which is not the production duplicate scenario.

**Severity**: Low. Interactions are additive per-digest by design. Duplicate digests adding a
second interaction row is harmless — it's extra data, not data loss. But it means the v3
interaction count can exceed expectations and should not be asserted as "exactly N."

### ⚠️ 3. Heartbeat test uses `StubChannel` but messages_access alert is a live alarm

The new heartbeat test (`ingest.test.ts`) proves the alert fires on a stub channel. This is correct
for the test. But the first time this alarm fires in production, it will go to a real user — and
the `LossEpisodeGate` is per-server-process, not per-deploy. A Railway restart resets it and could
re-fire.

**Severity**: Low. The gate is best-effort, not a durable guarantee. Acceptable for a v3.1 alarm.

### ⚠️ 4. `upsertOpenLoops` had a SECOND bug: 9 placeholders for 10 columns

STATE_V2 §7 documents this: "`upsertOpenLoops` generating 9 placeholders for a 10-column INSERT —
it could never insert a row." This is a DIFFERENT bug from the `base = params.length` off-by-one.
The migration added columns but the batch insert didn't reflect them. Fixed now, but it means
`upsertOpenLoops` was never functional for the entire history of this branch. The test that now
covers it (`batch-params.test.ts`) was written after the fix.

**Severity**: Historical. Fixed. But it and the `base = params.length` bug both existing
simultaneously in the same file means repository-v3.ts had zero functional multi-row paths.

### ⚠️ 5. `inbound-adapter.test.ts` — 8 compile errors were blocking every deploy

This file was on the "pre-existing, do not chase" list. It had 8 TypeScript errors. The
`Dockerfile` runs `tsc --noEmit` before build, so every deploy attempt failed at compile time.
Nobody noticed because deploys happen via `railway up`, not automatically.

**Severity**: Historical. Fixed now. But it reveals a process gap: files on the do-not-chase list
can silently block production deploys. The list should be audited for compile errors, not just
test failures.

The delta from V3_AUDIT.md is substantial: production deploy, real round trip, orphaned pipeline

real problems. The v2 path is still in place as the safety net.

**Three actions are the critical path to flipping the flag**: rebuild the app (contacts fix),
decide the redaction question, confirm v3 tables populate from a real sync.

**The deploy blocker** (`inbound-adapter.test.ts` compile errors) and **the heartbeat rejection**
(`additionalProperties: false`) are the poster children for why features behind a flag need to
deploy their schema and code even when the flag is off — these were caught by the act of deploying,
not by review.
