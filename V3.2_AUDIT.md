## 3. Redaction fix — deep audit

### What was broken

The phone pattern required only 7+ digits with separators (`/(?:+?\d[\d().\- ]{5,}\d)/`).
This matched `2026-08-10` (8 digit-chars plus dashes), bare 7–9 digit runs, scores, order
numbers, and ISO dates. **14 of 15 voice packs were rejected every sync.** Those packs
could never upload — the Mac resends identical bytes and gets identical 422s forever.

### What was fixed

Pattern changed to `/+?(?:[().\- ]*\d){10,}/` — requires at least 10 digit characters.
Measured against 173 real voice packs: all 14 false positives cleared.

### The legal cover

The original justification was "a false positive costs one rejected upload, which the Mac
retries after redacting properly." This was WRONG — the Mac does not re-redact on retry.
That repair step was never built. The assumption behind the original breadth did not hold.

### Residual risk (documented)

A bare 7-digit local number without country/area code (`555-0142`) no longer trips the
server-side guard. Guard one (Mac `Redaction.swift`) and guard three
(`check_voice_pack_leak.py`) still cover it. This is the correct tradeoff: 10 digits is the
shortest run that is a phone number more often than it is a date, score, or ID.

### Audit judgment

✅ Correct fix. The comment is honest about the residual risk and the broken assumption.
The decision to trade 100% coverage of 7-digit local numbers for zero false positives on
14/15 packs is right, given that two other guards catch the local-number case.

## 4. interaction_id fix — deep audit

### What was broken

The V3.1_AUDIT.md flagged this (item #2): `deterministicInteractionId` was keyed on
`digest_id`. Every sync mints a fresh `digest_id`, so the same "last contact with this
person" event got a brand new `interaction_id` on every sync. `ON CONFLICT … DO NOTHING`
never fired. `interactions` grew by one row per relationship per sync, all describing one
event, forever. Anything counting interactions would have drifted upward without bound.

### What was fixed

```diff
-function deterministicInteractionId(digest_id: string, person_id: string): string
+function deterministicInteractionId(person_id: string, occurred_at: Date): string
```

Now keyed on `person_id + occurred_at` — the event, not the digest that happened to carry
it. The same `(person, last_contact_at)` tuple always produces the same `interaction_id`,
regardless of which digest carried it.

### The test that proves it

New test: "does not duplicate interactions across SEPARATE syncs of the same event" —
inserts the same digest with TWO different `digest_ids` (as a real re-upload would),
asserts `second.interactions === 0` and total count stays at 5.

The old idempotency test is preserved — it re-uses one `digest_id` and still passes
because the new keying scheme is a superset (same `occurred_at` from the fixture).

### Audit judgment

✅ Correct fix. The root cause was correctly identified (V3.1 flagged this exact gap).
The fix is minimal — changing the hash input. The test proves the real scenario, not just
the artificial single-digest_id case. This is the right safety-net-to-fix ratio.

## 7. Items flagged (new from this audit)

### ⚠️ 1. No backfill for existing interaction_id rows

The interaction_id fix changed the hash function. Any `interactions` rows written by
the first deploy (which used `digest_id`-based IDs) have the old format. There are
presumably zero or few such rows (the v3 pipeline was only live for ~22 hours between
first and second deploy, and the user hadn't synced during that window). But there is
no migration or backfill script to clean up old-format rows if they exist.

**Severity**: Low. The window was small. But if any old-format rows exist, they will
persist until `deleteUser` or a manual cleanup.

### ⚠️ 2. Redaction comment still says "a false positive costs one rejected upload"

The file header at `redaction.ts:41` still reads: "A false positive costs one rejected
upload, which the Mac retries after redacting properly." This is the WRONG claim — the
Mac does NOT re-redact on retry. The fix's own comment (at the pattern level) correctly
contradicts this, but the file-level header is now misleading. The two claims in the same
file disagree.

**Severity**: Low. The behavior is correct (10-digit minimum). The comment is wrong.
Update the file header to match the pattern-level comment.

### ⚠️ 3. New worktrees detected — `v3/j-contracts`, `v3/k-graph`, `v3/m-pipeline`

Three new branches appeared since V3.1. These are unmerged and unknown to this audit.
The `j-contracts` branch may touch `chat_reply.v2` or add new schemas — these are part
of the frozen interface in V3_ARCHITECTURE.md §4. Any change to a frozen interface must
be logged in INTERFACES.md per the cross-session protocol.

**Severity**: None yet. Flagging as awareness, not a defect.
