# Shared Contracts — Boi

**Frozen as of:** the foundation commit on `main`.
**Owner of changes:** the user. No agent modifies this file unilaterally.

## How to use this file

You are one of four agents working on this project in parallel, in separate git
worktrees. You cannot see the other tracks' code and you must not depend on reading
it. Everything you need from them is specified here, literally.

Code against these definitions exactly as written. If your implementation needs
something this file does not specify, that is a **contract gap**: stop, commit your
work in progress, write the gap into your track's `NOTES.md`, and report it to the
user. Do not invent the missing piece and do not edit this file.

Section 11 lists what is deliberately **UNRESOLVED**, almost all of it downstream of
not having a Linq token yet. Read it before you assume something is missing by
accident.

## 0. What Boi is, in one paragraph

A consumer AI assistant that lives in iMessage. A companion Mac app reads the user's
local iMessage history, so Boi is the only assistant that knows their *relationships* —
who they're close to, who they're losing, who is waiting on a reply right now. Each
morning it texts a brief of at most three people, and for each one it drafts **two**
candidate messages in the user's own voice. It never sends them; the user does.

Three properties everything else depends on:

- **The corpus never moves.** 84,000 messages stay on the Mac. Only abstractions cross
  the boundary. Local SQL over the whole corpus takes under two seconds, so there is no
  upload, no progress bar, and no drop-off window.
- **The Mac is allowed to be asleep.** Staleness is a visible state, never a silent
  wrong answer.
- **Delivery does not depend on the Mac.** The cloud sends the morning text.

### The three shapes worth reading in full before you start

**`voice_pack.v1`** carries the user's **own sent messages**. It is the reason drafting
does not break the digest boundary: the voice we imitate is the user's, the content we
must understand is somebody else's, and those separate. Section 7 covers the guards.

**`gist.v1.facts`** is an allowlist, not decoration. It is the complete set of
specifics a draft is permitted to name. Anything outside it — a date, a time, a place,
an amount, a person — is an invented commitment sent in the user's own name.

**And it crosses the digest boundary, so it is subject to the no-verbatim rule.**
Tightened 2 Aug to **max 3 words and 40 characters per entry**, because a 60-character
cap let a place pattern capture four consecutive capitalised words and put
`"Jenny And Marks Wedding"` — the other person's sentence, verbatim — into the cloud
inside the object built to prevent exactly that. A specific is `the 14th`, `Friday`,
`$120`. It is never a phrase.

**Licensing is by anchored match, not substring containment.** `$120` in `facts` must
not license a draft that says `$12`, and `8/14/2026` must not license `8/14`. A
bidirectional `in` check licenses every prefix of every specific, which turns the
fabrication gate into a generator of *wrong* commitments in the user's own name — worse
than the invented ones it was built to stop.

**Vague temporal hedges are not specifics.** Decided 3 Aug after the gate rejected
`"ill get back to u this week"` on every model run — a 5% ceiling nobody could reach,
and prompt `05` rightly forbade touching a gate to improve a score.

The line: **a specific is falsifiable against a calendar; a hedge is not.** `Thursday`,
`the 14th`, `at 7`, `tomorrow` all commit the user to something that can turn out to be
wrong. `this week`, `soon`, `later`, `sometime`, `in a bit` commit to nothing checkable.
The gate exists to stop a plausible *wrong* commitment being sent in the user's name, and
a hedge cannot be wrong — it can only be vague, which is the entire point of the `defer`
stance.

So: a closed allowlist of hedges passes without needing a match in `facts`. Keep it
closed and keep it short; anything naming a day, a date, a time or a number is a
specific and stays gated.

**Known and bounded:** spelled-out numbers (`seven`, `the fourteenth`), abbreviated
weekdays (`next thurs`), lowercase places (`the ferry building`) and single first names
(`Sarah`) are not extracted today, so a draft can name them freely. Those are the four
highest-frequency fabrications in real texting. Ship it if you ship it, but say so on
the trust page rather than describing the gate as complete.

### `as_of` reaches the drafter, and stale state is never claimed in the present tense — added 4 Aug

**This rule existed in `BOI_ARCHITECTURE.md` § 6.6 from the beginning and never reached
this file, so no track could have built it, and none did.** `prompts.py` contained the
string `as_of` zero times: `render_gist()` emitted the situation, state, `days_silent`,
the question flag, topic, deadline and allowed specifics, and no timestamp. `SYSTEM` had
five rules and none concerned tense. Searching all of `prompts/` for "present tense"
returned nothing. That is a transcription failure in planning rather than a track defect,
and it is the reason this section exists.

**What it costs.** `days_silent` is computed when the digest is built. A Mac closed for
four days hands the model *"days since the last message: 3"* with no anchor and no
instruction to hedge, and the model writes *"sorry, been 3 days"* into a message **the
user sends in their own name**, on day seven. Staleness is handled correctly one layer up
— `staleness.ts` exists and `deliver.ts` puts the caveat first — but a caveat above a
draft that speaks confidently in the present tense is not a hedged draft. § 8 calls
staleness "structurally impossible to lose"; a rule carried only in a system prompt is not
structural.

Three requirements, and the third is the one that makes it true rather than requested:

1. **`as_of` is rendered into every drafter prompt**, with what it means beside it: every
   number in the gist was measured then, not now.
2. **`SYSTEM` forbids present-tense claims about stale state**, and names the remedy — "a
   while", "ages", "too long" — because a prohibition with no alternative is one a model
   routes around.
3. **A gate rejects a bare day count when the gist is stale**, whatever the model did.
   Stale is `as_of` older than `BOI_STALENESS_WARN_HOURS` (24), which is the same hour the
   brief starts telling the user its data is old; two thresholds would mean a warning
   above a confident draft. **A missing or unparseable `as_of` counts as stale** — wrongly
   hedging costs a vaguer message, wrongly not hedging sends a wrong one.

Hedges are untouched, per the rule above: a specific is falsifiable against a calendar and
a hedge is not, and a stale draft *should* hedge.

**`prompt_version` moves when the prompt does.** § 6 makes a bad draft reproducible from
`(voice_pack_version, gist_id, prompt_version, model_id)` and from nothing else, because
the prompt is never logged. Changing `SYSTEM` under a fixed version string makes that
tuple a lie. This change is `draft.v1` → `draft.v2`, and the committed transcripts under
`contracts/transcripts/model/` genuinely are `draft.v1` output.

### The hedge allowlist is a gate concern, not an extraction concern — clarified 4 Aug

The 3 Aug ruling above ("a closed allowlist of hedges passes without needing a match in
`facts`") was never implemented, and the canonical example it quotes is the one that
failed: `facts.RELATIVE_DAYS` extracts `this week` as a date, so **`"ill get back to u
this week"` failed `fabrication_gate` on every run against an empty allowlist** — the
exact 5% ceiling the ruling was written to remove.

The allowlist belongs in `validator.py` and not in `facts.py`. Extraction should keep
seeing these strings, because a gist's own `facts` may legitimately carry `this week` out
of the other person's message; it is the **gate** that must not treat them as
commitments. Closed and short: `this week`, `next week`, `this month`, `next month`,
`soon`, `later`, `sometime`, `in a bit`, `a while`. `tomorrow` and `the weekend` are
commitments and are deliberately absent.

### A guard that iterates a collection must state what an EMPTY collection means — added 4 Aug

`_quotes_the_corpus(text, inbound)` iterated `inbound` looking for overlap, so an empty
corpus meant "does not quote the corpus" for every input, including a sentence a model
invented outright. On the digest-driven path `recent_inbound_text` is **always** empty —
correctly, because `digest.v1` carries metadata and never prose — so the only guard on a
model-written gist besides a length check could not bite, and any hallucination under 140
characters would have become the brief item body a user reads.

It was latent only because no MLX backend is installed. **That is the argument, not the
mitigation:** a guard whose failure mode is invisible until a dependency appears will not
be found by testing.

So, two rules:

- **Every guard of the form "iterate a collection, pass if nothing matches" must say in
  its docstring what an empty collection means, and fail closed unless there is a reason
  not to.** The question `_quotes_the_corpus` really answers is "can I show this to
  somebody?", and with no corpus the answer is no.
- **Where a producer cannot work, refuse it rather than degrading into it.** The
  digest-driven gist path raises on a model producer instead of handing it an empty corpus
  and grading the output with a gate that cannot see anything.

### The length gate, corrected 2 Aug

The original spec said "within 2× the user's median message length." That is too tight
and it rejected the project's own reference drafts. The median is computed over every
sent message including `"ok"` and `"lol"`, a draft has to acknowledge the silence *and*
answer — structurally two clauses — and the register already records that this user sends
`avg_msgs_per_burst` messages at a time. A single draft standing in for a burst is
legitimately longer than one median message.

```
limit = max(median_len_chars * avg_msgs_per_burst, p90_len_chars) + 30
```

The `+ 30` is the apology opener, which costs about that much before the answer starts.
For the Maya pack (median 34, p90 88, burst 2.3) the limit is 118 — a 79-character defer
passes, and the 300-character paragraph the gate exists to catch still fails by a wide
margin. The tell was never 2×; it was closer to 9×.

**`draft_bundle.v1.candidates`** is **exactly two, or exactly zero.** Never one, never
three. The two must differ in **stance** (`answer` vs `defer`), not in phrasing — two
paraphrases of the same sentence is a fake choice and users notice immediately. Zero is
a legitimate degraded outcome when the validator refuses both after one retry. A brief
with no draft is fine. A brief with a bad draft is a trust event.

## 2. API surface

Full spec: `contracts/openapi/boi-api.v1.yaml`. Produced by **Track D**, consumed by
Track A (uploads) and Track C (webhook delivery).

| Endpoint | Purpose | Notable response |
|---|---|---|
| `POST /v1/digest` | upload a T0 digest | `202` · `409 {"error":"duplicate"}` on a repeated `generated_at` |
| `POST /v1/voice-pack` | upload one voice pack | `202` · **`422 {"error":"redaction_failed"}`** — pack rejected and NOT stored |
| `POST /v1/heartbeat` | Mac liveness | `204` |
| `POST /v1/pair` | six-digit code → device token + `user_salt` | `200` · `404 {"error":"invalid_code"}` |
| `DELETE /v1/users/{id}` | delete everything, derived data included | `204` |
| `POST /v1/webhooks/{provider}` | inbound from transport | `204` · `401 {"error":"bad_signature"}` |

**`/v1/webhooks/{provider}` lives in `cloud/api/`, ratified 2 Aug.** It was in the frozen
OpenAPI as Track D's surface but no prompt assigned it a path, and prompt `06`'s
constraints named `cloud/brief/`. Track D wired it into `cloud/api/` and recorded the
deviation, which is the right call: it belongs with the other HTTP routes, and the
signature guard has to sit next to the auth middleware rather than in the composer.

**It takes RAW BYTES.** `Channel.normalizeInbound(rawBody: Buffer | string, …)` — retyped
from `unknown` on 2 Aug, because `unknown` let Track C (which requires bytes, since a
signature verifies over bytes) and the foundation's `StubChannel` (which cast to an
object and read `.id`) disagree about what the first argument of a frozen interface
*means*, with the compiler silent. That is exactly the disagreement a type at a seam
exists to catch, and `StubChannel` now enforces it too — so a consumer can no longer
develop against a stub that tolerates what production rejects.

Behind Fastify: register a raw-body content-type parser **before** the JSON parser and
pass `req.rawBody`. Guard the header — `req.headers["x-boi-signature"]` is
`string | string[] | undefined`, and a missing one must become `401 bad_signature`,
never a 500.

Shared error bodies, every endpoint:

```json
{ "error": "validation", "detail": "string" }
{ "error": "unauthorized" }
```

### Signup is US-only at launch, and it is config — added 4 Aug

Both strategy documents state it in the same words: *"US only at launch. GDPR grants
non-users rights we structurally cannot fulfill."* Boi holds abstractions about people who
never signed up to anything, so a counterparty's right to erasure is one the architecture
cannot honour by construction — it cannot identify them.

`POST /signup` validated `/^\+[1-9][0-9]{6,14}$/`, which is every country on earth, and no
geo gate existed anywhere else. **The invariant was in both documents and in no code.**

The allowed set is `BOI_ALLOWED_COUNTRY_CODES`, default `1`. Config rather than a literal
because launch geography is a deploy decision: adding Canada is an env change, and adding
the UK is an env change plus a lawyer. A malformed number and a refused country must
produce **different messages** — otherwise a UK user is told their phone number is
invalid, which is both wrong and untrue.

## 3. Data schema

Owner: **Track D**. Migrations live at `cloud/db/migrations/` and only Track D writes
them.

Two properties are load-bearing and cannot be retrofitted once there is data:

```sql
-- Every table carries user_id and is partitioned on it, so delete is ONE operation
-- that covers derived data. CCPA is not optional, and one-click delete that leaves
-- derived rows behind is exactly the gap the FTC prosecutes.
create table users (
  user_id      text primary key,
  phone_e164   text not null unique,
  email        text,
  user_salt    bytea not null,     -- issued once at pairing, never rotated
  timezone     text not null default 'America/Los_Angeles',
  created_at   timestamptz not null default now()
);

-- contact_id = HMAC(user_salt, normalized_handle), computed ON THE MAC.
-- The same phone number produces a DIFFERENT id for every user, so cross-user joins
-- are arithmetically unavailable -- not "forbidden by policy" but unavailable to a
-- rogue query or a subpoena. This is the shadow-profile line rendered in schema.
-- The server NEVER sees a raw handle for anyone but the account holder.
create table relationships (
  user_id      text not null references users(user_id) on delete cascade,
  contact_id   text not null,
  display      text not null,
  payload      jsonb not null,     -- conforms to digest.v1 $defs/relationship
  as_of        timestamptz not null,
  primary key (user_id, contact_id)
) partition by hash (user_id);
```

**Never join users to each other.** If two users both text the same person, those rows
must not link. Crossing that line is what ended NGL.

### Correction, 2 Aug: cascade is the delete mechanism, not partitioning

The original wording of this section implied that hash partitioning by `user_id` is what
makes delete one operation. **It isn't, and that was a bad criterion.** A hash partition
holds many users, so there is no per-user partition to drop; `on delete cascade` from
`users` is what actually does the work, and it would have done it with no partitioning at
all.

The criterion was not free, either. It forced `users` itself out of the pattern — you
cannot keep `phone_e164 unique` on a table hash-partitioned by `user_id` — and it made a
global unique constraint on active pairing codes impossible.

So, corrected:

- **Required:** every user-data table carries `user_id` and cascades from `users`, and a
  single `DELETE FROM users WHERE user_id = $1` provably leaves zero rows anywhere.
  Verify by enumerating tables **from the catalog**, never a hard-coded list.
- **Optional, for scale:** hash partitioning on `user_id`. Keep it where it costs
  nothing. Do not contort a constraint to preserve it, and `users` is exempt.
- **The delete enumeration must not depend on a column being named `user_id`.** Prompts
  04 and 05 add `brief_items`-shaped tables keyed on a parent id with no `user_id` column
  of their own. A catalog query filtered on the column name cannot see those, which makes
  it a naming-convention checker wearing a catalog's clothes. Either give every table a
  `user_id`, or enumerate by walking foreign keys from `users`.
- **Derived data outside Postgres counts.** A rendered card at `briefs.card_url` is
  derived data; delete has to reach it too.

**`inbound.v1.user_id` is advisory. `from_handle` is authoritative.** Decided 2 Aug,
after Track D correctly declined to pick unilaterally because the choice changes
behaviour Track C relies on.

Track C populates `user_id` by calling an injected resolver over `from_handle`, so it is
a *derived* field. Track D must re-derive from `from_handle` itself and treat a mismatch
as a rejection, not a warning. Trusting a derivation you were handed, when you hold the
input it was derived from, is strictly weaker than re-deriving — and the failure mode is
acting on user A's behalf because a resolver said so.

This is defence in depth: the signature is the real gate, and a forged webhook cannot be
signed. But the signature proves *the provider sent this*, not *this handle belongs to
that account*, and those are different claims. Track C should keep populating `user_id`
— it is useful and it is right — and Track D should verify rather than consume it.

**`inbound.v1.reply_to_message_id` carries the PROVIDER's id** (`lmsg_...`), not Boi's
own outbound id (`omsg_...`). Track C normalizes what the webhook gave it and cannot know

## 6. Shared conventions

- **Times** are ISO 8601 UTC strings with a `Z`, at every boundary. No epoch integers
  cross a process line.
- **`as_of` on every fact, end to end** — digest, storage, prompt, tool result. It must
  be structurally impossible to lose, because the failure mode is Boi confidently
  saying something false about a person's friend.
- **IDs**: `usr_` users, `dev_` devices, `h_` contacts (HMAC hex), `g_` gists, `vp_`
  voice-pack versions, `omsg_`/`lmsg_` messages.
- **Naming**: `snake_case` in JSON, SQL, and Python; `camelCase` inside TypeScript
  code but `snake_case` on every wire shape; Swift properties match the JSON keys
  exactly so `Codable` needs no `CodingKeys`.
- **Errors**: `{ "error": "<slug>", "detail"?: string }`. Slugs are lowercase snake.
- **Logging**: structured JSON to stdout. **Log the prompt hash, never the prompt.** A
  bad draft must be reproducible from `(voice_pack_version, gist_id, prompt_version,
  model_id)` without a prompt log full of user content sitting in an observability
  vendor.
- **Tests** live beside the code (`*.test.ts`, `intelligence/tests/`,
  `mac/Tests/`).

### Cross-language determinism — Tracks A and B must agree exactly

Track A ships the Swift voice-pack extractor and Track B ships the Python reference.
They are diffed on identical input at integration, so every step that could round
differently has to be pinned. Three are:

- **Percentiles: nearest-rank, half-up.** On the ascending sorted list of length `n`,
  the p-th percentile is the element at 0-based index `ceil(p/100 * n) - 1`, clamped to
  `[0, n-1]`. Do **not** use a language's default rounding — Python's `round()` is
  banker's rounding and Swift's `rounded()` is half-away-from-zero, so `n = 20` gives
  index 18 in one and 19 in the other. Different `p90_len_chars`, different
  `voice_pack_version`, and a `--compare` diff nobody can explain.
- **`voice_pack_version` = `"vp_" + sha256(canonical_json)[:8]`**, where the payload is
  `{contact_id, scope, register, exemplars}` — `as_of` excluded — serialized with sorted
  keys, no whitespace, and **non-ASCII characters left unescaped** (`ensure_ascii=false`).
  Emoji in `top_emoji` make this matter.
- **Redaction runs on exemplars only, never before the register is computed.** See § 7.

### Product conventions that are not style preferences

- **Invitation, never verdict.** `"you've reached out to Sarah 12 times this month"`,
  never `"Sarah doesn't text you back"`. Every reveal ships with a one-tap remedy.
  Guilt without agency is repellent; guilt with a button is a product.
- **Never auto-send.** Ever. The approval tap costs nothing and buys everything.
- **Don't ship reciprocity.** Across 25 real relationships the spread was 0.465–0.615,
  sd 0.034 — it carries almost no information, and it is the most legally dangerous
  metric in the category. Momentum (0.0×–13.9×) is where the signal is.

  *Corrected 2 Aug:* several prompts asked for `grep -rin 'reciproc' <dir>` to return
  nothing. **That criterion is unsatisfiable and it was wrong.** The foundation's own
  `Contracts.swift` and `FoundationTests.swift` explain why the metric is excluded, a
  track cannot edit a frozen file, and build artifacts inherit the string. Worse, it
  punishes exactly the behaviour we want: documenting *why* a tempting metric is absent
  is how the decision survives the next engineer who rediscovers it.

  The real criterion: **no code computes it, and nothing renders it.** Verify by reading
  the metric library and the card's string list, not by grepping for a substring. A
  comment naming the thing you refused to build is evidence of judgement, not a
  violation.
- **Degrade, never fabricate.** No drafts beats bad drafts. A vague gist beats a
  hallucinated one. "Haven't seen your Mac since Sunday" beats a confident wrong
  answer.

### `is_from_me = 1`, guarded three times

Voice-pack exemplars must originate from message rows the **user wrote**. This is
asserted in three independent places, and all three ship:

1. **The SQL query** on the Mac (Track A) and in the reference builder (Track B).
2. **The upload boundary** — `POST /v1/voice-pack` returns `422 redaction_failed` and
   stores nothing (Track D).
3. **A test that fails the build** — `scripts/check_voice_pack_leak.py` (Tracks A and B
   both run it).

One inbound message riding along in an exemplar list makes every privacy claim in the
architecture false, and nobody would notice for months. **This is a frozen anchor. Do
not weaken any of the three to make a checklist green.**

Redaction, applied on the Mac before an exemplar is ever serialized: phone numbers,
email addresses, street addresses, dollar amounts, and third-party full names. A
redacted exemplar is just as good a style sample and carries none of the risk.

**Redaction covers every free-text field in the pack, not just `exemplars`.**
`register.apology_openers` is the one that catches people out: it holds *verbatim
message prefixes* — the committed fixture's are `"sorry been mia"` and `"omg sorry"` —
so a pack whose exemplars are spotless can still carry a phone number or a dollar amount
into storage through that array. `abbreviations` and `top_emoji` are free strings too.
Guard one (the Mac) and guard two (`POST /v1/voice-pack`, the `422`) must both scan
`exemplars`, `register.apology_openers` and `register.abbreviations`. A guard that
inspects one of four free-text fields is not the guard §7 claims it is.

**Redact the exemplars, not the corpus.** Compute the register from the raw sent
messages first, then redact only the strings that go into `exemplars`. Redacting first
corrupts the very statistics the pack exists to carry: `"Hey Sarah how are you"` becomes
`"[name] how are you"`, which stops counting as a greeting and flips the first character
to lowercase — so a sentence-case writer who opens with a name gets reported as
`lowercase_no_period` with a third of their true `greeting_rate`. Every register test
still passes and the register is wrong.

**Name redaction must not assume capitalization.** The target corpus is lowercase
texting — the fixture register is literally `lowercase_no_period`. A pattern requiring
`[A-Z]` passes every test written against capitalized samples and leaks
`"ill ask john smith about it"` untouched.

### Correction, 2 Aug: only guard one can see `is_from_me`

Calling all three "the `is_from_me` guards" was an overclaim, and it is the kind that
ends up in a privacy policy. **Nothing at the upload boundary can observe provenance.**
The server has no corpus; four regexes over free text cannot distinguish a message the
user wrote from one they received, and a redacted inbound message passes with `202`.

Stated accurately:

| | What it is | What it can actually see |
|---|---|---|
| **One — the Mac's SQL** | `is_from_me = 1` in the query | **provenance.** The only guard that can. |
| **Two — `POST /v1/voice-pack`** | a **redaction scan** over every free-text field | PII patterns. Not provenance. |
| **Three — `check_voice_pack_leak.py`** | a **verbatim string check** against the corpus | an `is_from_me` filter deleted outright. Not a redacted leak. |

So the real protection is **guard one, singular**, and guards two and three are a
redaction net and a regression alarm behind it. That is still a defensible posture — it
is defence in depth over a filter that must not silently disappear — but it is not three
independent checks on the same property, and nobody should describe it that way
externally.

**What this changes:** guard one is now the single point of failure, so it carries the
canary requirement alone. Any track shipping it must demonstrate the test failing with
the filter removed and passing with it restored. Do not weaken that on the theory that
two more guards are behind it.

### Guard one is `is_from_me = 1` **AND NOT A TAPBACK** — corrected 3 Aug

`is_from_me = 1` alone does not keep the other person's words out. **A tapback the user
sent carries `is_from_me = 1` and a body of `Loved "<their sentence>"`** — inbound prose,
verbatim, inside a row the user genuinely wrote.

Every other layer is blind to it:

- The serializer's re-assertion checks `isFromMe` only. Remove the tapback filter and the
  pack is written without complaint.
- **Guard two** finds no PII in `Loved "see you thursday"` and returns `202`.
- **Guard three** compares verbatim against inbound rows; `Loved "…"` is not byte-equal
  to the message it quotes, so it passes.
- **No fixture can generate the case.** `make_synthetic_chatdb.py` emitted every tapback
  as `is_from_me = 0` with `text = NULL`, so no test could have caught it. Fixed — the
  generator now produces a user-sent tapback quoting a distinctive inbound string.

So the single most sensitive path in the system was protected by one unasserted, untested
line that the other two guards could not see. The `is_from_me` canary was satisfied and
the property it existed to guarantee — *no inbound prose reaches an exemplar* — was not.

**Required, in the query and asserted again at the serializer:**

```sql
WHERE is_from_me = 1
  AND COALESCE(associated_message_type, 0) NOT BETWEEN 2000 AND 3999
```

and a canary that builds a mirror containing a user-sent tapback quoting a distinctive
inbound string, asserts that string is absent from every exemplar, and is verified to
fail with the filter removed.

*Note for whoever reads this later:* the tapback filter existed in more than one track as
a **statistics** guard — tapbacks poison length and burst metrics. Its privacy role was
incidental and undocumented, which is exactly why a future cleanup would have removed it
for statistical reasons and taken the last real protection with it.

### Guard three reads the MIRROR, not `chat.db` — corrected 3 Aug

It used to read `chat.db` and build its sent-set from `text IS NOT NULL`. On a real Mac
only about a third of rows have a `text` column — **9,940 of 30,998** on the corpus that
found this — because the rest live in `attributedBody`. So a phrase the user genuinely
sent was missing from the sent-set, and if anyone had ever said the same words back to
them, the checker called it a leak. **47 of 174 packs flagged, every one a false
positive.**

That is the ~47%-of-the-corpus trap the typedstream decoder exists to solve, reproduced
inside the script written to guard the corpus. And a guard that cries wolf on a quarter
of real users is worse than no guard — it teaches people to ignore it, which is exactly
how the real leak gets waved through.

`--mirror` is now the correct input. Pointed at a raw `chat.db`, the script measures the
NULL-text share and **refuses** rather than reporting a number it cannot stand behind.

### What guard three does and does not do

`scripts/check_voice_pack_leak.py` compares exemplars against inbound messages
**verbatim**. Anything redaction rewrote no longer matches and is reported as
`redacted beyond verbatim match`, which passes. So the third guard weakens exactly as
redaction gets more aggressive, and it is not independent of the first two in the way
"three guards" suggests: guards one and two live in the same process, and guard three is
a verbatim string check.

Stated plainly so nobody trusts it further than it goes: **guard three catches a whole
class of failure — an `is_from_me` filter deleted outright — and misses a redacted
inbound message.** It is a regression alarm, not a proof. The real protection is that
guards one and two are independent of each other and both demonstrably bite: a track
must show its canary test failing with the filter removed and passing with it restored.

### The decoder metric, corrected 2 Aug — and a truncation trap it exposed

The original criterion was "the share of messages with no recoverable text falls from
~47% to under 2%." **That measures how photo-heavy someone's corpus is, not whether the
decoder works,** and it conflates the two. Measured on a real 94,652-message corpus:

```
BEFORE (no decoder)   65.23%  unrecoverable
AFTER                  2.26%  = 2,143 rows
  attachment-only      1.73%  = 1,642   no text by nature
  no text, no blob     0.53%  =   501   nothing to recover
  blob undecodable     0.00%  =     0   <- actual decoder failures
```

A perfect decoder scores 2.26% against a 2% bar. So:

- **The bar is on decoder failures only:** rows where `attributedBody` is non-null and
  decoding yields no text, over rows where `attributedBody` is non-null. **Under 0.5%.**
  This is the number that says the typedstream port is correct.
- **`unrecoverableShare` stays reported, with no bar.** It is a genuine corpus statistic —
  a user whose messages are mostly photos is a real segment — and prompt `06`'s health
  check should see it. It is not a decoder metric and must never gate one.

Classify attachment-only rows from `cache_has_attachments` and `message_attachment_join`,
never from the decoder's own output. A decoder grading its own failures as "that one was
just a photo" is the exact self-exoneration this split exists to prevent.

### `first_contact_at` is a lie whenever the corpus is retention-capped

The same run found the span is **exactly 365 days**, floored at the boundary — Apple's
*Keep Messages = 1 Year* deleting everything older. So **every** `first_contact_at` in
that digest reads as the boundary date. A friendship that began in 2019 reports as
beginning a year ago.

That is not a rounding error, it is a false claim about someone's life, and the card is
built on being checkable against the user's own memory. Wrapped flopped precisely when
people started doubting the numbers.

**Required, Track A at digest time:** when `corpus.retention_boundary` is set and a
relationship's earliest message falls within a day of that boundary, emit
`first_contact_at: null`. The schema already permits null. Never emit the boundary date
as a first-contact date, and never let the card render "you met in August 2025" from a
truncated corpus.

Momentum, initiation ratio and the 90-day comparison are all unaffected — they are
windowed and never reach back past the boundary. `first_contact_at` and anything derived
from it are the only casualties.

### The one thing the fixtures cannot give you

`scripts/make_synthetic_chatdb.py` cannot produce real `attributedBody` **typedstream**
blobs. Apple's typedstream is an undocumented pre-plist `NSArchiver` format, and a
hand-rolled fake would let a broken decoder pass — which is the worst possible outcome,
because getting this wrong silently loses roughly **47% of the corpus** and reads as
"the report is thin" rather than as a bug.

So the decoder is verified against the developer's **own** `chat.db`, read-only, with a
metric rather than a fixture: the share of messages with no recoverable text must fall
from ~47% to under 2%. That check runs locally and commits nothing. See Track A prompt
`03`.

The fixture database does give you the **WAL** property, which is the other silent
killer:

```
mode=ro      -> 9637 rows
immutable=1  -> 9636 rows     # ignores the WAL, freezes the corpus, raises no error
```
